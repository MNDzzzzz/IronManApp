### 3. P1.3: Inserción por Lotes - "Día Típico Cumplido"

Para el tracking nutricional de un clic, requerimos una transacción segura en base de datos que maneje inserciones masivas y evite duplicidad de registros si el usuario ya introdujo una comida aislada ese día.

**Lógica de Deduplicación:**
Utilizaremos un identificador compuesto (ej. `userId_date_mealId`) en la base de datos (PostgreSQL/Supabase) con una restricción `UNIQUE`. El `BatchInsert` usará una estrategia `UPSERT` o `INSERT IGNORE`.

```typescript

export async function logTypicalDay(userId: string, date: string, typicalDayId: string): Promise<BatchInsertResult> {

  const typicalDay = await getTypicalDayPlan(typicalDayId);
  
  // Deduplicación en memoria antes del batch
  const mealsToInsert = typicalDay.meals.filter(
    m => !existingLogs.some(log => log.mealId === m.mealId)
  );
```

```typescript
export enum IntentType {

  LOG_WORKOUT = 'LOG_WORKOUT',

export class CoachCore {
  async triageMessage(userId: string, message: string) {
    // 1. NLP/LLM o Regex para extraer intención
    const intent = await this.analyzeIntent(message);

        return this.formatDiscomfortResponse(strategy);

      case IntentType.LOG_TYPICAL_DAY:

        return `¡Listo! He registrado tu día típico. Omití ${result.skippedMeals.length} comidas que ya habías registrado hoy.`;
        
      default:
```

### Resumen de Decisiones (Trade-offs)
*   **Separación de Responsabilidades:** El bot (`CoachCore`) no calcula adaptaciones ni guarda en BD directamente; delega en managers de dominio (`DiscomfortManager`, `NutritionService`). Esto permite que la interfaz gráfica (`GymView`) y la interfaz conversacional (`Coach`) reutilicen exactamente la misma lógica de negocio.
*   **Gestión de Estado (Deduplicación):** Se hace en dos capas: validación en memoria (para reportar al usuario qué se omitió) y restricción `UNIQUE` en base de datos para integridad referencial.
